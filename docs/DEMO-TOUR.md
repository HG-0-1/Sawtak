# MC2026 demo tour — judge-ready checklist

This is the live-demo path for the hackathon. The demo mode is deliberately labelled development mode: it uses a mock SMS provider and `access.mode=OFF` initially, so it is not a production configuration.

For a step-by-step presentation of QR presence and GPS verification, see [QR and location demo](./QR-LOCATION-DEMO.md). In particular, a successful phone GPS check requires a trusted HTTPS origin; the default plain-HTTP LAN demo is suitable for showing QR-only behavior, not reliable mobile geolocation.

## 1. Start everything

Open **PowerShell** in the project folder.

```powershell
Set-ExecutionPolicy -Scope Process Bypass
.\scripts\start-demo.ps1 -UseDocker -OpenDisplays
```

`-UseDocker` starts the Postgres container and exposes it locally on port `5433` so it does not conflict with a PostgreSQL service already using `5432`. Omit it only if PostgreSQL is already running at `localhost:5432`. The script is phone-ready by default: it discovers your laptop’s local Wi-Fi/Ethernet IP and writes it to the local `.env`, making the QR contain an address a judge’s phone can reach. `-Lan` remains supported, while `-LocalOnly` disables phone access. `-OpenDisplays` opens the QR and results pages along with the admin page.

If Windows asks about a firewall rule, allow the local/private-network prompt for Node. Do not use a public Wi-Fi for the demo unless its clients can reach one another.

The script opens the admin page and prints the demo username/password from `.env`. It does not auto-fill or expose credentials to the browser URL.

## 2. Browser layout for judges

Use three browser windows/tabs:

| Screen | URL | What to show |
|---|---|---|
| Entrance QR | `http://localhost:5173/display/qr` | The QR countdown and visible regeneration. |
| TV results | `http://localhost:5173/display/results` | Live vote totals. |
| Admin | `http://localhost:5173/admin` | Voting controls and live operations. |
| Visitor results | `http://localhost:5173/results` | Mobile live standings for a verified voter. |

Keep the QR and results tabs in full screen on separate displays if possible. Scan the **QR code**, not a hand-typed link, from a phone connected to the same Wi-Fi. At startup, the script verifies that the generated QR targets the LAN address and saves the current target in `.demo/current-qr-url.txt`. It must begin with `http://<your-lan-ip>:5173/p/v1.`.

## 3. The 3-minute happy-path demo

1. In the admin page, show that voting is **OPEN**.
2. On the entrance screen, point out the countdown. Wait for it to change once if time allows: the QR is short-lived and generated by the API.
3. Scan it from the phone. Enter a name, the judge-demo number `0795550143`, tick consent, and continue. Voters do not use a username/password. OTP requests are rate-limited to five per phone number per hour; if this number has been used repeatedly, use a fresh test number.
4. Enter `123456` (the local `DEMO_OTP_CODE`). No SMS is sent; this same demo code is valid for each newly requested challenge, which expires after five minutes. The phone number is a demo voter account and may be reused to sign in again; existing votes remain recorded.
5. Cast a vote in each category. Keep the TV screen visible; each committed vote changes the SSE result count without a refresh.
6. Tap **Live results** on the voter phone. The participant sees a mobile live-standings page; it updates from the same SSE stream and shows only aggregate counts.
7. In admin, pause voting, then reopen it. Export the results JSON or CSV.

## 4. Show the QR/presence control clearly

For the stronger QR-only part of the demo, after the initial happy path:

1. In **Admin → Settings**, edit `access.policy` and change only `"mode": "OFF"` to `"mode": "QR_ONLY"`; save.
2. Open a private/incognito phone browser directly at the visitor URL. It will be refused because it lacks the presence cookie.
3. Scan the current QR. The app redeems the signed token, strips it from the visible route, and lets the user continue.
4. Wait two minutes, then try an old copied `/p/...` link: it will report that the live code has expired.

For a real pilot, set `STRICT` only after configuring confirmed venue IP ranges and/or the real geofence. `OFF` and mock SMS are prohibited at production boot.

## 5. How to explain password and personal-data protection

Use this wording with judges:

> “Admin passwords are **hashed**, not encrypted, using Argon2id. A hash is one-way, so the database cannot reveal the password. Mobile numbers are different: we encrypt them with AES-256-GCM because an authorized export may need the original number; we also store a peppered HMAC hash for uniqueness checks. The voting API never logs OTP codes, raw phone numbers, QR tokens, or raw coordinates.”

If PostgreSQL runs in Docker, use this **read-only** command to demonstrate the password representation:

```powershell
docker compose exec postgres psql -U mc2026 -d mc2026 -c "SELECT username, left(password_hash, 28) AS stored_value FROM admins;"
```

The stored value starts with `$argon2id$`; it cannot be decrypted back to the original password.

To demonstrate the phone protection after one registration:

```powershell
docker compose exec postgres psql -U mc2026 -d mc2026 -c "SELECT name, encode(phone_enc, 'hex') AS encrypted_phone, encode(phone_hash, 'hex') AS lookup_hash, phone_last4 FROM visitors;"
```

The ciphertext/lookup hash is shown, along with only the last four digits for masked display. Do not project this command if it contains a real visitor’s name; use your own demo record.

## 6. Quick test tour

Before judges arrive, run:

```powershell
.\scripts\test-demo.ps1
```

This runs unit tests, a production build, the production-dependency audit, plus health/config/category/QR API checks against the started stack. Add `-FullJourney` to create one clearly labelled local test visitor and exercise OTP → three votes end-to-end:

```powershell
.\scripts\test-demo.ps1 -FullJourney
```

`-FullJourney` requires the initial development policy `OFF`. Run it before switching to `QR_ONLY` for the QR-control demonstration.

Then test manually:

- QR URL changes after the countdown.
- New phone/private tab can scan, request OTP, verify, and vote three times.
- The fourth/second vote for an already-voted category is rejected.
- Results update on the TV without page reload.
- Admin pause blocks a subsequent vote; reopen restores voting.
- Results export downloads.

## 7. Troubleshooting

| Symptom | What to do |
|---|---|
| Script says Postgres is unavailable | Use `-UseDocker`, start Docker Desktop, or start local Postgres at port 5432. |
| QR phone cannot open the link | Run with `-Lan`, confirm same Wi-Fi, disable client/AP isolation, and allow Node through the Windows private-network firewall. |
| QR shows “connection” state | Check `http://localhost:3000/readyz` and `.demo/api-error.log`. |
| Admin page does not load | Read `.demo/web-error.log`; restart using `stop-demo.ps1`, then `start-demo.ps1`. |
| Wrong OTP | Check `DEMO_OTP_CODE` in your local `.env`, then request a fresh code. |
| Need a clean ballot set | Run `npm run demo:reset`; history remains in the database by design. |

## 8. Stop the demo

```powershell
.\scripts\stop-demo.ps1
docker compose down  # only if you also want to stop Postgres
```

`docker compose down` keeps the database volume. Add `-v` only when you intentionally want to erase the local demo database.
